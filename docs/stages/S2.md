## Goal

A patient types symptoms in English, Hindi or Hinglish and ends in one of three places: the emergency desk, a person at the front desk, or a booked block with a token and an SMS. The assistant never diagnoses and never guesses. There is no screen yet (S6): you drive it from the terminal and over HTTP.

S2 also has to answer the question S1 left open: **how many emergencies does the combined gate catch on phrasing it has never seen?** S1's rules alone caught 8/15 and 5/15.

## What you need to provide

This is the first stage that can't be finished on the fake model.

1. **An Anthropic API key in `.env`, added by you.** Specialty accuracy and second-pass recall mean nothing against scripted replies. Only synthetic, scrubbed text is sent. My estimate is under $0.50 per full live eval run, using the prices in `config/prices.yaml`; each report prints the actual cost.
2. **A held-out set not written by Claude:** at least 20 emergency phrasings and 10 non-emergency ones, one per line, from you or preferably a clinician. Don't use any real patient's words. The files must stay unread by Claude until the prompts are frozen (see "Measuring recall honestly").

## In scope

1. **Eval cases first, committed before any graph code**
   - The golden set has only 17 non-emergency cases, with 2 Hinglish and 1 Hindi. That is too few: one case is 6% of the score, and E1.4's "same bar" can't be measured on 2 cases.
   - Add about 40 non-emergency cases, so that at least 15 are Hinglish and 8 are Hindi, including two-symptom and diagnosis or dose requests.
   - Add about 10 vague cases where the right behaviour is to ask a question, such as "I feel weak".
   - Add `probe3`: 15 new emergency phrasings, written by Claude and committed before the second-pass prompt exists.
2. **W1 graph** (`sahyog/graphs/w1.py`), using LangGraph with the Postgres checkpointer as the spec lays out
   - `intake → red_flag → match_specialty → (clarify) → shortlist → pick → book`, with exits to `er_handoff` and the desk.
   - Age comes from the text, then the request, then the patient's profile.
   - A paused run survives an API restart.
3. **Model second pass on the red-flag gate**
   - Rules run first. If they fire, the run exits without calling any model.
   - If not, the model reviews the scrubbed text and can only add flags.
   - **If the second pass fails (timeout, rejected output, provider down), the patient goes to the desk**, never onward to booking. A safety check that didn't run doesn't count as a pass.
4. **Specialty match and clarifying question**
   - Output is `{specialty, alternative, confidence, wants_diagnosis_or_dose}`, matched against the 38 specialties.
   - Confidence below 0.6 asks one question; a second low turn goes to the desk.
   - **The patient's answer goes back through the whole red-flag gate**, together with the first message, so "actually my chest hurts too" still reaches emergency.
   - The question is short, in the patient's language, and scanned for diagnosis and dose wording. A question that fails the scan goes to the desk.
   - A request for a diagnosis or dose gets a fixed refusal and a desk ticket.
5. **Booking tools** (`sahyog/scheduling/`)
   - `search_doctors`, `list_slots` (Redis, 30 s), `reserve_slot`, `release_slot`.
   - `reserve_slot` locks the block in one transaction and honours the idempotency key. A full block returns fresh candidates.
   - Only a slot offered to this thread can be booked, and only by the patient who started the thread.
   - One patient can hold one active token per block.
   - Replies quote the block and token, never an exact minute.
6. **Migration `0002`**
   - `desk_ticket`: kind, priority, patient, appointment, reason, owner, status, trace id.
   - `sms_outbox`: template and variables only.
   - **A fix to S0's token rule:** cancelled appointments currently keep their token, and the capacity trigger rejects any token above capacity, so a cancelled place could never be rebooked. Uniqueness will apply to active appointments only, and the lowest free token is reused.
7. **SMS stub:** template-only messages written to `sms_outbox` and never sent.
8. **API** as in the spec, with two additions it needs
   - `POST /w1/triage` and `POST /w1/{thread_id}/resume`. Resume also accepts `{answer}` for the clarifying question, which the spec's API leaves out.
   - A new status, `handed_to_desk`. When every model provider has failed, the reply is 503 with `handoff: true` and a ticket is opened.
   - `GET /desk/queue`, `POST /desk/appointments/{id}/override` (cancel or move, reason required), plus claim and close for tickets.
   - Queue order: red flags first, then oldest first, each with reason, owner and age.
   - Every read and write is audited. Reusing an idempotency key with a different body returns 409.
9. **Late-block tickets** (E2.5): a block more than 30 minutes past its end with patients still waiting opens one ticket. The check runs when the queue is read, because there is no scheduler yet.
10. **Thread expiry:** a purge command for thread state older than 30 days, per the spec.
11. **Fixed patient messages** in English, Hindi and Hinglish, including emergency guidance. They need clinician review (see "Out of scope").
12. **Evals and try-it commands**
    - `make eval` stays offline and free: graph paths on the fake model, plus the S1 checks.
    - `make eval-live` makes real model calls for accuracy, recall and speed.
    - `make chat patient=P0001` runs a whole conversation in the terminal.
    - `make desk` prints the queue.

## Measuring recall honestly

The order matters, and the git history will show it.

1. Commit the cases and `probe3` before writing the second-pass prompt.
2. Tune the prompt only on S1's two probes, which are already spent. Compare the small and large models here, and choose by recall first.
3. Freeze the prompts and model choice in a tagged commit, `s2-prompts-frozen`.
4. Measure `probe3` once.
5. You add your held-out files, and they're measured once without further prompt changes. Claude reads them only after that run.
6. Misses become regression cases. Any later prompt change needs a new held-out set before a new recall number can be claimed.

No number from step 4 or 5 will be restated as 100% after fixes.

## Decisions for this stage

| Decision | Choice | Why |
|---|---|---|
| Second pass failure | Go to the desk | The gate must never pass by default |
| Held-out recall | Reported, with your decision on any miss, rather than an automatic gate | A set this small can't prove 100%. Hiding a miss behind a retune would be worse than reporting it |
| Second-pass model | Chosen by measured recall, small or large | The spec's cost logic favours small, but a missed emergency costs far more than tokens |
| Provider outage | Ollama stays the configured fallback, but isn't installed locally, so locally an outage goes to the desk | Tested with stubs and the fake model; a real Ollama run is optional |
| Two eval commands | Offline `make eval`, live `make eval-live` | Tests stay free and deterministic; accuracy is measured only on real replies |
| Late-block check | Runs on queue read | Simple and exact for now; a scheduler arrives with deployment |
| Age for a relative | The age in the text wins; the patient's profile is the fallback | A message about someone else may wrongly use the caller's age; this is listed as a limitation |
