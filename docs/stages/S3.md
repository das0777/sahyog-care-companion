## Goal

A patient uploads a report PDF and sees its status. Within 60 seconds its text is stored against that patient and can be searched, including scanned pages. S4 builds question answering on top of this, so S3 has to get three things right: the right text, the right page and the right patient.

**A misread number is the main risk.** If OCR reads an HbA1c of 7.2 as 1.2, every later answer will quote it faithfully, with a correct citation, and be wrong. S3 measures this directly and marks every OCR-read chunk so that S4 can say so.

## What you need to provide

Nothing to start. **S3 calls no outside model, and costs nothing to run.**

- **Disk:** the build adds OCR and a local embedding model, about 2–3 GB (my estimate; the test pack will give the real figure).
- **Later, ideally:** a few anonymised real report scans from Sahyog. Claude's synthetic scans will be cleaner than a phone photo of a crumpled report, so they can't show real-world OCR quality.

## In scope

1. **Eval set first, committed before any ingest code** (`evals/w2/`)
   - A deterministic generator makes synthetic PDFs from seeded patients: lab reports, discharge summaries and prescriptions. Synthetic data only.
   - Variants: text, scanned, mixed text and scanned pages, multi-page tables, Hindi, skewed, blurred and low-resolution scans.
   - Each PDF has a truth file listing every lab value, medicine and date, and the page each is on.
   - Bad files: corrupted, encrypted, not really a PDF, empty, too large, too many pages.
   - Red-team PDFs: instructions in visible text, in white or tiny text, and in Hindi.
2. **Upload** (`POST /w2/documents`, `GET /w2/documents/{job_id}`)
   - The patient comes from the token, never the request. Returns 202 with a `job_id`, as in the spec.
   - Checks the file really is a PDF, at most 20 MB and 50 pages, and not encrypted. These limits are my proposal.
   - Stored in MinIO under a key the server generates. Idempotency key as in S2.
   - Status: `queued`, `parsed`, `indexed` or `failed`, plus one addition, `held` (item 6). A reply also gives pages read, how many used OCR, chunks indexed, chunks quarantined and a plain failure reason.
   - **Caregivers are denied in S3.** Consent is enforced in S4, and failing closed is safer, as in S0.
3. **Queue and worker**
   - A separate `worker` service with a bounded pool of workers. Jobs are claimed from Postgres with `FOR UPDATE SKIP LOCKED`, so no new queue system is needed and the upload and its job commit together.
   - A crashed worker's job is picked up again after a timeout, up to 3 attempts, then `failed`. A retry can't duplicate chunks, because indexing replaces a document's chunks in one transaction.
4. **Ingest graph** (`sahyog/graphs/w2_ingest.py`)
   - `load → parse → (ocr) → identity_check → chunk → injection_scan → embed → index`.
   - **Parse page by page:** a page with a usable text layer uses it, and any other page goes to OCR, so mixed PDFs work.
   - **OCR:** Tesseract with English and Hindi, inside the boundary. Chunks read by OCR are marked `source = 'ocr'`.
   - **Chunks:** about 1,200 characters, split by report section. **A chunk never crosses a page**, so a citation's page number is always right.
5. **Local embeddings**
   - A multilingual model with 1,024 dimensions, as the schema expects, running inside the worker. **Report text never leaves the boundary for embedding.** Which model depends on measured speed and search quality, and the test pack will name it.
   - Cached by content hash, so re-uploading a PDF doesn't re-embed it.
6. **Wrong-patient check (not in the spec; my addition)**
   - If a report's ABHA number or name clearly belongs to someone else, it is `held`, not indexed, and a desk ticket opens.
   - Otherwise, a mix-up at upload would put someone else's results in this patient's answers, and the patient filter wouldn't help, because the chunks would be filed under the wrong patient.
   - A report with no name on it isn't held.
7. **Prompt-injection scan**
   - Patterns in English, Hindi and Hinglish run over extracted text, including hidden text. Flagged chunks go to `quarantined_chunk`: never indexed, counted in the status, and visible to the desk.
   - **This is a first filter, not the defence.** A paraphrased instruction will get through. S4's defences are the SQL patient filter and the citation check, and its red-team PDF tests those.
8. **Search** (`sahyog/records/search.py`)
   - `retrieve_records(query, k)`: keyword and vector search combined, with `WHERE patient_id = :ctx` in SQL. Every search writes an audit event per document read.
   - S3 uses it to prove a report is searchable, and S4 builds answers on it. There's no patient-facing endpoint until S4.
9. **Try-it commands**
   - `make w2-samples` generates the sample PDFs.
   - `make upload file=… patient=P0001`, `make doc-status job=…`, `make search patient=P0001 q="HbA1c"`.
   - `make eval` gains the checks below.
10. **Docs:** ADR on local embeddings and the Postgres queue, data contracts for the new tables, README section.

## Decisions for this stage

| Decision | Choice | Why |
|---|---|---|
| Embeddings | Local model in the worker | Report text is identified. Scrubbing it first would weaken search, and sending it unscrubbed would break the boundary. Slower than an API, so D1 and D2 will show whether it fits in 60 s |
| OCR | Tesseract, local, English and Hindi | Free, in-boundary, and it reads Hindi. Weaker than a cloud service on poor scans, which is why D5 is measured |
| Queue | Postgres, not a new service | The upload and its job commit together, and the stack needs nothing new. May need revisiting under load in S7 |
| Worker runs apart from the API | Yes | OCR and embedding would otherwise starve triage on the same process |
| OCR confidence | Marked per chunk, never hidden | A misread number can't always be detected, so S4 must be able to say a value came from a scan |
| Storing identified text | Chunks keep identifiers, inside the boundary | The gateway scrubs them on the way out in S4. This is the spec's design, and the token map stays on-prem |
| Eval order | Truth files and search questions committed before ingest code. Prompts aren't involved | The S2 slip came from one author writing both sides in one session. It can't be fully avoided here, because Claude writes both, so your own PDF in D20 is the independent check |
